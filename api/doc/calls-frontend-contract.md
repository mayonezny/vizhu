# ВИЖУ — контракт бэкенда звонков для фронтенда

Документ описывает API серверного контура звонков (auth → матчинг → LiveKit),
чтобы собрать фронт без доступа к истории обсуждения. Всё ниже выписано из
реального кода модуля `calls` (`calls.controller.ts`, `calls.service.ts`,
`calls.gateway.ts`, `matching.service.ts`).

**Что уже готово на бэке (трогать не нужно):** OTP-авторизация, защищённый выпуск
LiveKit-токенов (роль определяется сервером по БД), WebSocket-матчинг (presence
волонтёров, очередь незрячих, сведение пары в комнату), self-hosted LiveKit SFU.

**Что делает фронт:** UI под две роли + подключение к сокету матчинга + подключение
к LiveKit-комнате по полученному токену.

---

## 1. Конфигурация / адреса

| Что | Значение |
|-----|----------|
| REST API base | `https://app.vizhu.su/api` |
| Socket.IO | `https://app.vizhu.su` (путь по умолчанию `/socket.io/`) |
| LiveKit ws URL | **не хардкодить** — сервер возвращает его в ответах (`wss://rtc.vizhu.su`) |

Всё на одном домене через nginx — CORS не нужен.

---

## 2. Два разных токена (ключевое, не путать)

В системе ходят **два токена с разными задачами**:

1. **auth-JWT** — «кто ты в ВИЖУ». Выдаётся при логине (`/auth/verify-otp`).
   Живёт 7 дней. Идёт в заголовке `Authorization: Bearer <auth-JWT>` для REST
   и в `auth: { token }` при подключении сокета.
   Payload: `{ sub, phone, iat, exp }` (где `sub` = uuid телефонного аккаунта).

2. **LiveKit-токен** — «пропуск в конкретную комнату с правами по роли».
   Выдаётся бэком (эндпоинт `/calls/token` или приходит в событии `call:matched`).
   Живёт 30 минут. Только он пускает в LiveKit-комнату.

Цепочка: **auth-JWT → бэк выписывает LiveKit-токен → им заходим в комнату.**
Пользователь про LiveKit-токен не знает — фронт получает его под капотом.

> Фронт предполагается уже умеющим логин по OTP и хранящим auth-JWT.
> Форму ответа `/auth/verify-otp` сверь в `auth.controller.ts` (поле с токеном).

---

## 3. REST: `POST /api/calls/token`

Нужен для ручного подключения к комнате (в основном флоу токен приходит через
сокет — см. `call:matched`). Полезен для тестов и для «прямого входа в комнату».

**Запрос:**
```
POST /api/calls/token
Authorization: Bearer <auth-JWT>
Content-Type: application/json

{ "room": "test-room" }
```

**Ответ:**
```json
{ "url": "wss://rtc.vizhu.su", "room": "test-room", "token": "<LiveKit-JWT>" }
```

Роль (blind/volunteer) сервер берёт из БД (`user.role`), **не из запроса** — клиент
не может назначить себе права. От роли зависит, что разрешено публиковать (см. §7).

---

## 4. Socket.IO — подключение к матчингу

```ts
import { io } from 'socket.io-client';

const socket = io('https://app.vizhu.su', {
  auth: { token: authJwt }, // ← auth-JWT, НЕ LiveKit-токен
});
```

Gateway верифицирует токен и по `sub` грузит юзера. Битый/отсутствующий токен →
сервер сразу дизконнектит сокет. Роль юзера сервер знает сам — фронт роль не шлёт.

**Реконнект (важно для фронта).** socket.io-client переподключается сам с backoff'ом
— это не отключать. Серверное состояние привязано к `userId`, а не к сокету, и держит
**grace-окно 12 сек**: короткий обрыв связи (метро, переключение сети) не выкидывает
юзера из пула/очереди. Но при реконнекте id сокета меняется, поэтому фронт обязан
восстановить свой статус на событии `connect` — см. §6a.

---

## 5. События сокета

### Клиент → сервер (emit)

| Событие | Payload | Кто шлёт | Действие |
|---------|---------|----------|----------|
| `volunteer:online` | — | volunteer | Встать в пул готовых принимать звонки |
| `call:request` | — | blind | Запросить помощь |
| `call:accept` | `{ requestId }` | volunteer | Принять входящий звонок |
| `call:decline` | `{ requestId }` | volunteer | Отклонить входящий |

Серверные гварды: `volunteer:online` игнорируется у не-волонтёра, `call:request` —
у не-незрячего. Роль проверяется по БД, подделать нельзя.

### Сервер → клиент (on)

| Событие | Payload | Кому | Значение |
|---------|---------|------|----------|
| `call:waiting` | — | blind | Волонтёров нет, поставлен в очередь |
| `call:searching` | — | blind | Кандидат найден, звоним ему |
| `call:incoming` | `{ requestId, blindUserId }` | volunteer | Входящий звонок |
| `call:matched` | `{ url, room, token }` | обоим | Пара сведена — данные для входа в LiveKit |
| `call:cancelled` | — | volunteer | Незрячий отменил/отключился до ответа |

**`call:matched` содержит всё для подключения к LiveKit** (`url`, `room`, `token`) —
отдельный запрос к `/calls/token` в основном флоу не нужен.

---

## 6. Полный флоу «незрячий зовёт помощь»

1. Оба клиента подключают сокет с auth-JWT.
2. Приложение волонтёра шлёт `volunteer:online`, когда волонтёр готов принимать.
3. Незрячий жмёт «позвать помощь» → `call:request`.
4. Незрячему приходит `call:searching` (или `call:waiting`, если свободных нет).
5. Волонтёру приходит `call:incoming { requestId, blindUserId }` → показываем экран
   «входящий звонок» с «принять»/«отклонить».
6. Волонтёр жмёт «принять» → `call:accept { requestId }`.
7. Обоим приходит `call:matched { url, room, token }`.
8. Оба подключаются к LiveKit по `url` + `token` и публикуют треки по роли (§7).

### Крайние случаи (обрабатываются сервером, фронт реагирует на события)

- Волонтёр отклонил / не ответил за **20 сек** → незрячему пробуется следующий
  волонтёр; если свободных нет → `call:waiting`.
- Короткий обрыв сокета (< 12 сек) → юзер **не** выпадает из пула/очереди, состояние
  восстанавливается на реконнекте (см. §6a).
- Незрячий пропал дольше grace → волонтёр получает `call:cancelled`, освобождается.
- Волонтёр пропал дольше grace → незрячему ищется другой.

Фронту важно: показывать статусы из событий и уметь отменить свой запрос (просто
дизконнект сокета — сервер почистит состояние после grace-окна).

## 6a. Реконнект — что обязан делать фронт

Сервер переживает короткий обрыв сокета (grace 12 сек) и умеет передоставить матч
на новый сокет. Но восстановление статуса — ответственность клиента.

**1. На событии `connect` восстанавливать своё состояние.**
`connect` у socket.io срабатывает и при первом коннекте, и при каждом реконнекте.
Обработчик должен идемпотентно пере-заявить, кто ты:

```ts
socket.on('connect', () => {
  if (role === 'volunteer' && readyToTakeCalls) socket.emit('volunteer:online');
  if (role === 'blind' && isRequestingHelp)      socket.emit('call:request');
  if (inActiveCall)                              socket.emit('call:resume');
});
```

Сервер задедуплит: повторный `call:request` игнорируется, если юзер ещё в очереди
или в дозвоне; повторный `volunteer:online` просто подтверждает присутствие.

**1a. Уход волонтёра с линии — явное событие `volunteer:offline`.**
Перед разрывом сокета волонтёр обязан послать `volunteer:offline` — иначе grace
12 сек держит его в пуле, и незрячим уходят звонки в мёртвый сокет.

**2. Передоставка матча — только по запросу `call:resume`.**
Сервер больше НЕ шлёт `call:matched` сам на каждый коннект (это уводило свежий
звонок в комнату прошлого: обработчик коннекта срабатывает раньше нового
`call:request`). Клиент посреди активного звонка после реконнекта сокета шлёт
`call:resume` — сервер повторит `call:matched`, если матч ещё жив. Матч хранится
**60 сек** и гасится немедленно при новом `call:request`, `volunteer:online`,
`volunteer:offline` или истечении grace. `call:matched` по-прежнему обрабатывать
идемпотентно: если уже подключён к LiveKit-комнате с этим `room` — игнорировать.

**3. Реконнект самого звонка (LiveKit) — отдельный слой.**
Медиа-переподключение держит LiveKit сам, фронт только реагирует на события комнаты:

```ts
room.on(RoomEvent.Reconnecting, () => announce('Переподключаюсь…'));
room.on(RoomEvent.Reconnected,  () => announce('Связь восстановлена'));
room.on(RoomEvent.Disconnected, () => { /* звонок завершён → исходный экран */ });
```

Для незрячего `announce()` = `aria-live` и/или TTS (см. §8) — визуальные индикаторы
бесполезны.

**Итого два независимых слоя реконнекта:** сокет матчинга (восстанавливаем статус
сами на `connect`) и медиа звонка (LiveKit сам, мы только озвучиваем состояние).

## 7. Подключение к LiveKit-комнате

Библиотека: `livekit-client` (или `@livekit/components-react`).

```ts
import { Room } from 'livekit-client';

const room = new Room();
await room.connect(url, token); // url и token — из call:matched (или /calls/token)
```

**Публикация по ролям** (гранты уже ограничены сервером в токене, публикуем
соответственно):

| Роль | Публикует | Подписывается |
|------|-----------|---------------|
| `blind` | камера + микрофон | аудио волонтёра |
| `volunteer` | только микрофон | видео+аудио незрячего |

Смысл: незрячий шарит камеру, волонтёр видит картинку и голосом подсказывает.
Комната ограничена 2 участниками, пустая закрывается через 60 сек.

LiveKit сам держит качество (адаптация битрейта, ICE restart, simulcast, авто-
реконнект) — фронту это разруливать не нужно.

## 8. Требования к accessibility (критично — юзеры незрячие)

Интерфейс **незрячего** пользователь не видит вообще. Это не «доп. фича», а базовое
требование ВИЖУ:

- **Экран незрячего минимален:** одна крупная кнопка «позвать помощь», голосовые
  статусы, кнопка «завершить». Всё управляемо без зрения.
- **Озвучивание статусов:** каждое изменение состояния (ищем / волонтёр найден /
  соединено / завершено) сообщать через `aria-live="assertive"` регион И/ИЛИ TTS
  (в проекте есть Yandex SpeechKit — можно проговаривать голосом).
- **Голосовое управление:** запуск «позвать помощь» должен триггериться голосом —
  это одна из ключевых фич ВИЖУ.
- **Аудио/тактильные сигналы** на состояния звонка (дозвон, соединено, сброшено):
  визуальные индикаторы для незрячего бесполезны.
- **Фокус-менеджмент:** при смене экрана переводить фокус на главный элемент.
- **Крупные таргеты**, единственное основное действие на экране.

Интерфейс **волонтёра** — обычный визуальный (волонтёры зрячие): экран «входящий
звонок» с принять/отклонить, затем видео с камеры незрячего + управление
микрофоном/сбросом.

## 9. Как проверить бэк без фронта

Матчинг проверяется двумя socket.io-клиентами (нужны два auth-JWT: у одного юзера
`role=blind`, у другого `role=volunteer`). Сделать себя волонтёром для теста:

```sql
UPDATE users SET role='volunteer' WHERE phone='79xxxxxxxxx';
```

Мини-скрипт `test-match.js` эмулирует обе стороны: волонтёр шлёт `volunteer:online`,
незрячий — `call:request`, волонтёр ловит `call:incoming` и шлёт `call:accept`, оба
получают `call:matched` с одинаковым `room`. Совпадение `room` = матчинг рабочий.

Для проверки самой комнаты: взять `token` из `call:matched` (или из `/calls/token`)
и зайти на `https://meet.livekit.io` (режим Custom: URL + token).

## 10. Осознанные упрощения текущей версии (флажки на будущее)

- Состояние матчинга — **в памяти процесса** (один инстанс api). Grace-таймеры и
  матчи тоже в памяти → **рестарт api рвёт активные звонки** (после рестарта юзеры
  просто переподключат сокет и заново позовут). При горизонтальном масштабировании
  выносится в Redis.
- Дозвон **последовательный** (по одному волонтёру), таймаут 20 сек. Broadcast-ring
  (звонить всем сразу) — потом, если волонтёров мало.
- Реконнект-стойкость матчинга **есть** (grace 12с по `userId`, передоставка матча
  60с). Медиа-реконнект держит LiveKit. Не покрыт только рестарт самого api (см.
  первый пункт).

Всё это наращивается поверх, ломать текущий контракт не потребуется.

## 11. Что фронту сверить в коде бэка (не завязано на этот документ)

- Точная форма ответа `/auth/verify-otp` — где именно лежит auth-JWT.
- Имя первичного ключа сущности `User` (в `identity` LiveKit-токена кладётся именно
  он) — по коду это `user.uuid`.
- Глобальный префикс API (`/api`) — публичные URL уже с ним (`/api/calls/token`).
