# Задача: перенести матчинг звонков на Redis

> Детальный порядок реализации, модель ключей, тестовые сценарии и условия
> выкатки: [`redis-matching-implementation-plan.md`](redis-matching-implementation-plan.md).

## Зачем

Сейчас всё состояние матчинга живёт в полях класса `MatchingService`
(`api/src/modules/calls/matching.service.ts`) — обычные `Map` и `Set` в памяти
процесса. Отсюда два следствия:

1. **Рестарт api теряет всё.** Волонтёры «пропадают» с линии, незрячие
   вылетают из очереди, активные дозвоны рвутся. Деплой в рабочее время
   сейчас невозможен.
2. **Второй инстанс api поднять нельзя.** Каждый процесс видел бы только свою
   половину пользователей.

Цель — пережить рестарт без потери очереди. Горизонтальное масштабирование —
приятный побочный эффект, но **не** самоцель (см. «Чего делать НЕ надо»).

## Железное ограничение: контракт не меняется

`api/doc/calls-frontend-contract.md` — договор с фронтом. Набор событий, их
имена и полезная нагрузка **остаются прежними**:

- клиент → сервер: `volunteer:online`, `volunteer:offline`, `call:request`,
  `call:accept`, `call:decline`, `call:resume`;
- сервер → клиенту: `call:waiting`, `call:searching`, `call:incoming`,
  `call:matched`, `call:cancelled`.

Фронт (веб, Android, iOS) не пересобирается и не правится вообще. Если по ходу
работы кажется, что без нового события не обойтись — это повод остановиться и
обсудить, а не менять контракт.

## Что нужно сделать

### 1. Redis в инфраструктуре

В `infra/docker-compose.yml` сервис `redis` сейчас под профилем `max`, а
`depends_on: redis` у api закомментирован — то есть в проде Redis просто не
поднимается. Убрать профиль, вернуть зависимость с healthcheck.
`REDIS_URL` уже прописан в обоих compose-файлах, менять его не нужно.

### 2. Вынести состояние за интерфейс

Сейчас в `MatchingService` шесть полей состояния:

| Поле | Что хранит | Чем становится в Redis |
| --- | --- | --- |
| `online` | userId → socketId | hash |
| `available` | свободные волонтёры | set |
| `pending` | очередь незрячих (FIFO) | list |
| `ringing` | requestId → активный дозвон | hash (значение — JSON) |
| `graceTimers` | отложенная чистка после обрыва | ключ с TTL |
| `pendingMatch` | матч для передоставки | ключ с TTL 60с |

Правильный порядок работ: **сначала** описать интерфейс хранилища
(`MatchingStore`) и переложить на него текущую реализацию в памяти — так, чтобы
всё продолжало работать как раньше. И **только потом** писать вторую
реализацию поверх Redis. Так на каждом шаге есть рабочее состояние, и есть с
чем сравнивать поведение.

### 3. Таймеры

Три таймера сейчас живут в `setTimeout` и умирают вместе с процессом:
`RING_TIMEOUT_MS` (20с — волонтёр не ответил), `GRACE_MS` (12с — окно на
реконнект), `MATCH_KEEP_MS` (60с — хранение матча).

Grace и хранение матча переводятся на TTL-ключи Redis — они по своей природе
«протухание», ничего дополнительно делать не нужно. Таймаут дозвона требует
действия по истечении (передать вызов следующему волонтёру), поэтому его надо
либо повесить на keyspace notifications, либо на периодический sweep раз в
секунду. Sweep проще и для одного инстанса совершенно достаточен.

### 4. Флаг переключения

Переменная `MATCHING_BACKEND=memory|redis`, по умолчанию `memory`. Нужна,
чтобы выкатить код на прод, ничего не меняя в поведении, а переключаться
отдельным действием — и так же мгновенно откатываться.

### 5. Тесты

- Прогон эмулятора `npm run sim:matching` — все сценарии зелёные на обеих
  реализациях (`MATCHING_BACKEND=memory` и `=redis`).
- Jest-тесты на redis-реализацию: очередь FIFO, идемпотентность повторного
  `call:request`, истечение grace, истечение хранения матча.

## Чего делать НЕ надо

- **Не трогать фронт.** Совсем.
- **Не добавлять распределённые блокировки и Lua-скрипты.** Инстанс api один,
  гонок между процессами физически нет. Это можно будет добавить позже, когда
  (если) появится второй инстанс.
- **Не подключать `@socket.io/redis-adapter`.** Он нужен только для нескольких
  инстансов; сейчас он ничего не решает, но добавляет точку отказа.
- **Не переписывать логику матчинга.** Алгоритм (кому отдать вызов, что делать
  при отказе) остаётся ровно тот же — меняется только место хранения.

## Как проверять локально

Полный стек не нужен: матчинг не зависит ни от фронта, ни от LiveKit, ни от SMS.

```bash
docker compose -f infra/docker-compose.yml -f infra/docker-compose.dev.yml up -d postgres redis
cd api && npm ci && npm run start:dev

# в другом терминале
npm run sim:matching                    # все сценарии
npm run sim:matching happy resume       # выборочно
```

Эмулятор (`api/test/matching-sim.mjs`) поднимает два socket.io-клиента,
изображает волонтёра и незрячего и проверяет события контракта. Тестовые
учётки он заводит сам, телефоны `7000000000X` — с живыми не пересекаются.

Состояние в Redis по ходу теста удобно смотреть глазами:

```bash
docker compose -f infra/docker-compose.yml exec redis redis-cli KEYS 'matching:*'
docker compose -f infra/docker-compose.yml exec redis redis-cli SMEMBERS matching:available
```

## Критерии приёмки

1. `npm run sim:matching` зелёный при `MATCHING_BACKEND=memory` и при `=redis`.
2. **Главный сценарий:** волонтёр на линии, незрячий в очереди → перезапуск api
   (`docker compose restart api`) → после переподключения сокетов волонтёр
   по-прежнему на линии, очередь на месте, звонок доходит.
3. Контракт не изменён (диффа в `calls-frontend-contract.md` быть не должно).
4. Переключение между реализациями — только переменной окружения, без пересборки.
5. Фронт не затронут (диффа в `front/` быть не должно).

## Деплой

Делает владелец проекта, доступ к серверу исполнителю не нужен. Порядок:
мердж → сборка образа → выкатка с `MATCHING_BACKEND=memory` (поведение прежнее)
→ проверка, что ничего не сломалось → переключение флага на `redis` в тихое
время → прогон smoke-сценариев вдвоём → при любой проблеме флаг обратно.
