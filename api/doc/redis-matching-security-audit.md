# Аудит безопасности Redis-матчинга

Дата проверки: 27 августа 2026. Область: API звонков, Socket.IO-шлюз,
`RedisMatchingStore`, Docker-конфигурация Redis/LiveKit и production-зависимости
API. Это аудит исходного кода и локальной конфигурации; он не заменяет проверку
боевого хоста, Nginx/WAF, прав доступа к Docker и настроек LiveKit в облаке.

## Итог

В код внесены четыре исправления, исключающие обнаруженные уязвимые сценарии
в новом матчинге:

1. Только пользователь с ролью `VOLUNTEER` может послать `call:accept` или
   `call:decline`; `requestId` принимается только в формате UUID v4.
2. Все фоновые команды Socket.IO, включая отключение сокета, перехватывают
   ошибку и записывают её в лог. Необработанное отклонение Promise больше не
   может незаметно завершить процесс.
3. Захват активного ring выполняется одним Lua-скриптом Redis. Из двух
   одновременных `call:accept` только один получит ring и создаст LiveKit-токены.
4. Старый сокет не может удалить запись о новом сокете пользователя во время
   переподключения: условное удаление также стало атомарным Lua-скриптом.

После исправлений успешно пройдены `tsc --noEmit`, ESLint и 9 из 9 unit/
Redis-интеграционных тестов. Остаточные риски ниже требуют отдельной задачи
перед включением `MATCHING_BACKEND=redis` в production.

## Методика

- Ручная проверка путей Socket.IO: аутентификация, роли, входные данные,
  обработка ошибок и выдача LiveKit-токенов.
- Проверка состояний и конкурентных операций Redis: online socket, очередь,
  ring, reconnect grace и match TTL.
- Проверка production/dev Docker Compose и сетевой экспозиции Redis.
- `npm audit --omit=dev --json` и сверка фактически зафиксированных версий
  зависимостей (`npm ls`).
- Поиск секретов в исходном коде и конфигурации, без `node_modules` и lockfile.

## Открытые находки

### Критический — уязвимые production-зависимости

`npm audit --omit=dev` сообщает 12 уязвимостей: 1 critical, 9 high, 2 moderate.
Самая серьёзная — `tar@7.5.15`, используемый через `bcrypt` →
`@mapbox/node-pre-gyp`; audit помечает диапазон до `7.5.20` как critical.

Также затронуты `@fastify/static@9.1.3`, `@nestjs/platform-fastify@11.1.27`,
`@nestjs/swagger@11.4.5`, `axios@1.16.0`, `find-my-way`, `js-yaml`,
`socket.io-parser@4.2.6` и `typeorm@0.3.30`. Среди последствий audit указывает
обход авторизации/обход пути статических файлов, DoS/небезопасную обработку
URL и генерацию миграций TypeORM.

Автоматический `npm audit fix --dry-run` не применим: он останавливается на
конфликте peer-зависимостей между `@nestjs/platform-fastify@11.2.3` и
`@fastify/static@9.x`. Не следует запускать его с `--force`: сначала нужно
обновить согласованный набор Nest/Fastify и проверить приложение.

**Приёмка исправления:** в отдельной задаче обновлены совместимые версии
Nest/Fastify/Swagger/Socket.IO/TypeORM, `tar` не ниже безопасной версии из
audit; `npm audit --omit=dev` не содержит critical/high; прошли build, unit,
e2e и matching simulation.

### Высокий — Redis в production без аутентификации и TLS

В `infra/docker-compose.yml` Redis принимает подключения по
`redis://redis:6379`, без `requirepass` и TLS. Порт не опубликован наружу, что
снижает риск, но любой контейнер в `backend_net` может читать/подменять очередь
и временные LiveKit JWT из `matching:v1:match:*`. В dev Redis дополнительно
опубликован на `6379` хоста.

**Приёмка исправления:** Redis доступен по отдельному сильному секрету,
`REDIS_URL` у API и AI содержит учётные данные через безопасный механизм
секретов; healthcheck аутентифицирован; production Redis не имеет опубликованного
порта; доступ к сети разрешён только необходимым сервисам. Если Redis вынесен
за пределы одной машины, обязательны TLS и ACL с минимальными правами.

### Высокий — нет ограничения частоты Socket.IO-событий

JWT проверяется до подключения, роли проверяются, но нет лимита подключений и
событий `call:request`, `call:accept`, `call:decline`, `volunteer:online`.
Авторизованный пользователь может создать нагрузку на Redis, БД при handshake
и LiveKit при принятии звонка.

**Приёмка исправления:** лимиты на уровне Nginx/WAF по IP и на уровне gateway
по `userId`/socket; превышение возвращает предсказуемую ошибку и логируется без
JWT, номеров телефонов и LiveKit-токенов; есть тест на отказ при превышении.

### Высокий — горизонтальное масштабирование не поддержано полностью

Атомарный `takeRing` уже безопасен между инстансами, но составные процессы
`requestHelp` (проверить состояние → выбрать волонтёра → создать ring) и
`drainQueue` пока не защищены распределённой блокировкой/одним Lua-скриптом.
При двух API-инстансах возможны два ring для одной заявки или потеря порядка
очереди. Кроме того, Socket.IO adapter для межинстансной доставки событий не
подключён.

**Приёмка исправления:** до запуска более одного API-инстанса реализованы
атомарные transition-скрипты или lock по пользователю, подключён
Redis-адаптер Socket.IO, и проведён нагрузочный тест с двумя API-процессами.
До этого ограничение: **только один экземпляр API с Redis-матчингом**.

### Средний — LiveKit JWT хранится в Redis 60 секунд

Ключи match содержат room URL и LiveKit JWT до 60 секунд, а сам LiveKit-токен
выпускается на 30 минут. TTL Redis уменьшает окно утечки, но удаление ключа не
отзывает уже выданный JWT.

**Приёмка исправления:** Redis защищён как выше; TTL LiveKit-токена соответствует
политике риска; при требовании немедленного отзыва предусмотрен механизм
отзыва/короткоживущих токенов на стороне LiveKit.

### Средний — JSON из Redis проверяется только синтаксически

`RedisMatchingStore.parse` проверяет JSON, но не схему полей. Повреждённое или
подменённое валидное JSON-значение может привести к неверной маршрутизации.

**Приёмка исправления:** перед использованием проверяются типы и формат всех
полей `PendingRequest`, `ActiveRing`, `MatchInfo`; невалидная запись удаляется,
фиксируется безопасный лог и не останавливает sweep.

### Средний — `synchronize: true` и миграции TypeORM

В `src/app.module.ts` включён `synchronize: true`; одновременно установленная
`typeorm@0.3.30` затронута advisory, связанным с генерацией миграций.

**Приёмка исправления:** в production `synchronize: false`, схема меняется
проверенными миграциями; TypeORM обновлён в рамках исправления зависимостей.

## Положительные результаты

- Redis-ключи отделены префиксом `matching:v1`; match имеет TTL, а grace — TTL
  и индекс дедлайна.
- В production Redis не опубликован на host; сервисы разделены на frontend и
  backend сети.
- Socket.IO аутентифицирует handshake JWT до `handleConnection`; роль слепого
  пользователя уже ограничивает `call:request`, а волонтёра — статус online.
- `accept`/`decline` дополнительно сравнивают волонтёра с владельцем ring;
  room создаётся по серверному UUID, не из входных данных клиента.
- В репозитории не найдены реальные ключи или пароли; встречаются ссылки на
  переменные окружения и известные development-значения.
