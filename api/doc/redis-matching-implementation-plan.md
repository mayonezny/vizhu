# План внедрения Redis для матчинга звонков

## 0. Цель, рамки и инварианты

Цель — перенести изменяемое состояние матчинга звонков из памяти процесса API в
Redis так, чтобы очередь и статус пользователей переживали рестарт API. Алгоритм
матчинга и фронтенд-контракт остаются неизменными.

Исходные документы:

- [`calls-frontend-contract.md`](calls-frontend-contract.md) — неизменяемый
  договор с web, Android и iOS-клиентами;
- [`redis-matching-task.md`](redis-matching-task.md) — исходная постановка;
- `api/src/modules/calls/matching.service.ts` — эталон текущего поведения.

### Непересматриваемые ограничения

1. Не менять названия, payload и семантику событий Socket.IO.
2. Не вносить изменений в `front/`.
3. Не подключать `@socket.io/redis-adapter`: на этапе внедрения API работает в
   одном экземпляре.
4. Не добавлять распределённые блокировки и Lua-скрипты. Операции должны быть
   простыми и читаемыми; защита от повторных команд сохраняется на уровне
   существующей бизнес-логики.
5. Переключение реализации — только `MATCHING_BACKEND=memory|redis`, значение
   по умолчанию — `memory`.
6. Redis недоступен при `MATCHING_BACKEND=redis` — API не должен считаться
   готовым принимать звонки. Ошибку необходимо явно логировать и отражать в
   health/readiness-проверке, а не молча откатываться в memory.

### Что именно переносится

| Состояние | Текущее поле | Требуемое поведение после переноса |
| --- | --- | --- |
| активный сокет пользователя | `online` | `userId → socketId`; на реконнекте socket ID заменяется |
| свободные волонтёры | `available` | множество пользователей, готовых принять новый звонок |
| очередь запросов | `pending` | FIFO; при повторе запрос не дублируется |
| активный дозвон | `ringing` | связь request, незрячего, волонтёра, комнаты и deadline |
| окно реконнекта | `graceTimers` | 12 секунд до бизнес-очистки пользователя |
| матч для реконнекта | `pendingMatch` | данные LiveKit-токена с TTL 60 секунд |

> Важно: истечение TTL grace-ключа не вызывает серверный код само по себе.
> Поэтому sweep обязан обрабатывать и просроченный grace, выполняя эквивалент
> текущего `purge(userId)`. Для match достаточно TTL: после удаления ключа нет
> побочного действия. Для ringing sweep обрабатывает deadline и запускает retry.

## Часть 2. Redis в инфраструктуре и конфигурации API

### Работы

1. В `infra/docker-compose.yml` убрать профиль `max` у `redis`.
2. Вернуть `api.depends_on.redis.condition: service_healthy`.
3. Оставить AOF и volume `redis_data`; для матчинг-состояния настроить политику
   памяти осознанно. `allkeys-lru` может удалить живую очередь при дефиците
   памяти, поэтому для рабочего контура предпочтительны отсутствие eviction
   (`noeviction`) и мониторинг памяти либо отдельно согласованный лимит.
4. Добавить `MATCHING_BACKEND=memory` в production и development Compose,
   `.env.example` (если он есть) и документ конфигурации.
5. Создать Redis-провайдер в API на базе уже установленного `ioredis`:
   один клиент для команд, подключение по `REDIS_URL`, явный `connect/ping` на
   старте, корректный `quit` на остановке модуля.
6. Добавить readiness-проверку зависимости: в redis-режиме `/health` должен
   возвращать ошибку, если Redis недоступен; в memory-режиме Redis не является
   обязательным для health API.

### Приёмка части

- `docker compose ... up -d redis` поднимает Redis без `--profile max` и
  `redis-cli ping` отвечает `PONG`.
- API в режиме `memory` запускается при остановленном Redis.
- API в режиме `redis` ждёт healthy Redis; при недоступности Redis старт/health
  завершается предсказуемой ошибкой, а не работой с пустым memory-state.
- В diff нет файлов `front/` и изменений Socket.IO-контракта.

## Часть 4. Реализация RedisMatchingStore

### Предлагаемая схема ключей

Использовать единый префикс, например `matching:v1:`. Версия в ключе упрощает
безопасный сброс/миграцию формата в будущем.

| Ключ | Тип Redis | Значение и TTL |
| --- | --- | --- |
| `matching:v1:online` | hash | `userId → socketId` |
| `matching:v1:available` | set | `userId` свободных волонтёров |
| `matching:v1:pending` | list | JSON `PendingRequest`; FIFO через `LPUSH` + `RPOP` либо эквивалентно |
| `matching:v1:pending:by-blind` | hash | `blindUserId → requestId`; индекс дедупликации |
| `matching:v1:ring:{requestId}` | string JSON | `ActiveRing` без таймера |
| `matching:v1:ring:by-blind` | hash | `blindUserId → requestId` |
| `matching:v1:ring:by-volunteer` | hash | `volunteerId → requestId` |
| `matching:v1:ring:deadlines` | sorted set | `requestId → deadline epoch ms` |
| `matching:v1:grace:{userId}` | string | TTL 12 с, payload: прежний socket ID/время |
| `matching:v1:grace:deadlines` | sorted set | `userId → deadline epoch ms` для sweep и purge |
| `matching:v1:match:{userId}` | string JSON | `MatchInfo`, TTL 60 с |

Индексы `by-blind`/`by-volunteer` нужны, чтобы не сканировать все ring-ключи
при идемпотентности, `purge` и уходе волонтёра. В Redis не использовать `KEYS` в
рабочем коде.

### Работы

1. Реализовать все методы `MatchingStore` в `RedisMatchingStore` на `ioredis`.
2. Сериализовать JSON централизованно, с валидацией при чтении. Повреждённое
   состояние логировать с именем ключа и удалять/изолировать безопасно, чтобы
   один ключ не останавливал матчинг.
3. Сохранять ring до отправки `call:incoming`; удалять его только после
   валидного accept/decline/timeout/purge. Это сохраняет идемпотентность.
4. Для FIFO не допускать дубликатов: индекс `pending:by-blind` ставится при
   постановке в очередь и снимается, когда заявка взята в дозвон либо удалена
   в `purge`.
5. Не хранить auth- или LiveKit-токены в логах. `MatchInfo` содержит LiveKit
   JWT; ключи `match:*` должны иметь обязательный TTL 60 с и быть доступны
   только API в закрытой сети.
6. Документировать TTL и формат каждого ключа непосредственно рядом с
   реализацией.

### Приёмка части

- Команды в `redis-cli` показывают корректные ключи после каждого состояния:
  online, available, pending, ringing, grace и match.
- Очередь остаётся FIFO: два незрячих получают волонтёра в порядке заявки.
- Повторный `call:request` не добавляет второй элемент ни в list, ни в индекс.
- `call:accept` от другого волонтёра или с несуществующим requestId не меняет
  Redis-состояние.
- `match:*` исчезает максимум через 60 секунд; в Redis не появляется ключ с
  бессрочным LiveKit JWT.

## Часть 5. Обработка времени: sweep и восстановление после рестарта

### Работы

1. Добавить сервис sweep (один `setInterval`, период 1 секунда) и запускать его
   только при `MATCHING_BACKEND=redis`. На завершении Nest-модуля очищать
   interval.
2. На каждом тике получать из sorted set записи с deadline `<= now`:

   - **ring:** атомарно забрать/удалить запись, затем выполнить существующий
     `retry(request)`;
   - **grace:** убедиться, что пользователь не успел переподключиться, затем
     выполнить существующий `purge(userId)`;
   - **match:** отдельной обработки нет, Redis TTL удаляет ключ сам.

3. Сделать обработчики идемпотентными: повторный sweep или просроченная запись
   не должны второй раз освободить волонтёра, поставить в очередь или отправить
   `call:cancelled`.
4. При `userConnected` заменить socket ID, снять grace-key и запись deadline.
   Сохранённый до рестарта старый socket ID не считать активным — посылать
   событие можно только по socket ID, зарегистрированному в текущем процессе.
5. При старте redis-режима выполнять первый sweep сразу. Это обрабатывает
   deadline, истёкшие за период недоступности API, и предотвращает вечные ring.
6. Не пытаться восстановить транспорт Socket.IO из Redis. Клиент уже обязан
   переподключиться и переотправить `volunteer:online`, `call:request` или
   `call:resume` согласно существующему контракту.

### Приёмка части

- Непринятый звонок переходит к следующему волонтёру примерно через 20 секунд
  (допустимое отклонение — период sweep плюс задержка планировщика).
- Отключившийся незрячий после 12 секунд вызывает один `call:cancelled` у
  волонтёра и освобождает его.
- Отключившийся волонтёр после 12 секунд возвращает заявку в подбор следующего
  кандидата.
- После restart API сохранённые pending/ring/grace-deadline обрабатываются,
  когда клиенты реконнектятся; нет зависших заявок или дублей событий.

## Часть 6. Автотесты и сценарии приёмки

### Работы

1. Оставить `api/test/matching-sim.mjs` чёрным ящиком: запустить его для
   `memory` и `redis`, не меняя frontend-контракт.
2. Добавить Jest-тесты `RedisMatchingStore` с настоящим Redis в Compose либо
   отдельным тестовым Redis. Тесты очищают только ключи `matching:test:*`, не
   используют `FLUSHALL`.
3. Добавить интеграционные тесты `MatchingService` с fake `CallsService`:
   accept, decline, timeout, grace purge, реконнект и переотдача match.
4. Добавить сценарий рестарта: создать очередь и доступного волонтёра, завершить
   API без очистки Redis, запустить снова, переподключить клиентов и дождаться
   доставки звонка.
5. Добавить smoke-проверку инфраструктуры: API не стартует раньше healthy
   Redis в redis-режиме; volume Redis сохраняется между пересозданиями
   контейнера.

### Матрица обязательной приёмки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Нет волонтёров | один `call:waiting`, заявка однажды поставлена в FIFO |
| Волонтёр появляется | первая заявка переводится в `call:incoming`/`call:searching` |
| Два незрячих | порядок назначения соответствует FIFO |
| Повтор `call:request` после reconnection | в очереди/дозвоне остаётся одна заявка |
| Decline/timeout | заявка повторно подбирается следующему волонтёру |
| Grace < 12 с | состояние сохраняется, сокет заменён, purge не срабатывает |
| Grace ≥ 12 с | выполняется ровно один purge с теми же событиями, что в memory |
| `call:resume` до 60 с | приходит тот же `call:matched`; после 60 с — не приходит |
| Рестарт API | очередь и дедлайны не теряются, клиенты восстанавливаются существующими emit |
| Redis отключён в redis-режиме | readiness/error предсказуемы, нет незаметного memory fallback |

### Приёмка части

- `MATCHING_BACKEND=memory npm run sim:matching` — зелёный.
- `MATCHING_BACKEND=redis npm run sim:matching` — зелёный.
- Все добавленные Jest-тесты зелёные и запускаются повторно без утечек ключей.
- Дифф `api/doc/calls-frontend-contract.md` пуст; в `front/` изменений нет.

## Часть 7. Выкатка и откат

### Работы

1. Выпустить код с `MATCHING_BACKEND=memory`. Проверить логин, Socket.IO,
   добровольца, вызов и LiveKit: поведение обязано совпадать с текущим.
2. Проверить Redis: health, AOF/volume, свободная память, отсутствие eviction
   живых matching-ключей, доступ API только из `backend_net`.
3. В тихое время поменять только переменную окружения на
   `MATCHING_BACKEND=redis` и перезапустить API.
4. Провести smoke-сценарий двумя пользователями: очередь → рестарт API →
   реконнект → звонок; затем accept и соединение с LiveKit.
5. Наблюдать первые сутки: Redis errors, длительность sweep, количество
   просроченных ring/grace, размер `matching:v1:*`, 5xx API и ошибки Socket.IO.
6. План отката: вернуть `MATCHING_BACKEND=memory`, перезапустить только API.
   Не удалять Redis-ключи до завершения анализа инцидента; ключи имеют TTL,
   а новый префикс версии позволит очистить их позднее адресно.

### Финальные параметры приёмки

1. Контракт из `calls-frontend-contract.md` не изменён, frontend не
   пересобирался и не менялся.
2. Memory- и Redis-реализации проходят один набор симулятора и тестов.
3. При рестарте API не теряются очередь, готовность волонтёра и deadline
   незавершённого дозвона; после штатного Socket.IO-реконнекта звонок доходит.
4. Все операции, создающие side effect по времени, восстановимы после рестарта:
   ring timeout и grace purge обслуживаются sweep; match удаляется TTL.
5. Redis не доступен извне Docker-сети, данные persistent в volume, а Redis
   недоступность заметна по readiness и логам.
6. Откат к прежнему поведению выполняется изменением одного параметра
   `MATCHING_BACKEND=memory` без пересборки образов и без правок клиента.
